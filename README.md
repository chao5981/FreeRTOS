  这一节主要讲解RAM的内存管理，如果对RAM,ROM，Flash，SRAM这些东西理解不清晰的话，请到"chao5981/stm32f103-main-MDK文件类型详解"中复习。

  栈和堆空间都属于RAM空间。

  我们在FreeRTOS中，分为静态创建和动态创建，如果采用静态创建，那么占用的空间位置就由自己决定;如果是采用动态创建，那么占用的空间就是堆空间。

  一般的，我们都习惯用动态创建，因为相比于静态创建而言实在是太方便了，那么freertos是如何管理堆空间的呢?

  FreeRTOS 操作系统将内核与内存管理分开实现，操作系统内核仅规定了必要的内存管理函数原型，而不关心这些内存管理函数是如何实现的，所以在 FreeRTOS 中提供了多种内存分配算法（分配策略），但是上层接口（API）却是统
一的。这样做可以增加系统的灵活性：用户可以选择对自己更有利的内存管理策略，在不同的应用场合使用不同的内存分配策略。

  FreeRTOS 的 V9.0.0 版本为我们提供了 5 种内存管理算法，分别是 heap_1.c、heap_2.c、heap_3.c、heap_4.c、heap_5.c，源文件存放于FreeRTOS\Source\portable\MemMang 路径下，在使用的时候选择其中一个添加到我们的
工程中去即可。

  下面介绍这几个版本的内存管理方法有什么不同:

  1. heap_1.c
  实现：极简实现。只实现了 pvPortMalloc()，没有实现 vPortFree()。分配过程只是简单地将堆空间向上偏移。
  
  特点：
  
  不可释放内存。一旦分配，内存就无法被释放。
  
  确定性（执行时间固定）且不会产生碎片。
  
  代码量小，开销极低。
  
  适用场景：
  
  安全性要求极高的嵌入式系统（如工业级），这些系统通常在启动后创建所有任务、队列等，之后便不再删除它们。
  
  从不会删除一个内核对象的应用。

2. heap_2.c
实现：使用最佳匹配算法（Best Fit algorithm）和一个空闲块链表来管理堆。不支持内存合并（Coalescence）。

  什么是最佳匹配算法呢?比如我们申请 100 字节的内存，而可申请内存中有三块对应大小 200 字节， 500 字节和 1000 字节大小的内存块，按照算法的最佳匹配，这时候系统会把 200 字节大小的内存块进行分割并返回申请内存
的起始地址，剩余的内存则插回链表留待下次申请

特点：

可以释放内存。

会产生内存碎片。尤其是当申请的内存大小频繁变化时，碎片化会非常严重。因为释放的块不会与相邻的空闲块合并。

不确定性：分配时间取决于空闲链表的状态。

适用场景：

FreeRTOS 官方现已不推荐使用，因为 heap_4.c 是更好的选择。

曾经适用于那些反复创建和删除任务，但每次分配的内存大小都相同的应用（如总是创建相同大小的任务），这样可以避免碎片。

3. heap_3.c
实现：它只是对标准库的 malloc() 和 free() 进行了一层简单的封装（通过暂时挂起调度器来保证线程安全）。

特点：

使编译器自带的堆管理变得线程安全。

依赖编译器的内存管理实现，其行为和特性（如碎片、速度）因编译器而异。

链接器设置的堆大小生效，configTOTAL_HEAP_SIZE 配置无效。

很可能增大 RTOS 内核的代码大小。

适用场景：

在已经有成熟内存管理的桌面或大型嵌入式平台上移植 FreeRTOS。

需要利用编译器提供的某些高级内存管理特性时。

4. heap_4.c
实现：使用首次适应算法（First Fit algorithm）和一个空闲块链表。最关键的是，它支持内存合并。当块被释放时，它会自动与相邻的空闲块合并成一个更大的块。

特点：

可以释放内存。

极大地减少了内存碎片的问题，是通用性最强的推荐方案。

具有 xPortGetMinimumEverFreeHeapSize() 函数，非常有助于评估堆大小是否设置合理。

不确定性，但效率很高。

适用场景：

绝大多数需要动态创建和删除内核对象的应用。

申请和释放的内存大小具有随机性的应用。

5. heap_5.c
实现：在 heap_4.c 的基础上，增加了管理多个不连续内存区域的能力。

特点：

具备 heap_4 的所有优点（首次适应、内存合并等）。

通过 vPortDefineHeapRegions() 函数，可以将分散在内存地址空间中的多个、不连续的存储区域配置为一个统一的堆。

适用场景：

内存布局复杂的系统。例如，将高速内部 RAM 和低速外部 RAM 组合使用。

系统中存在多个物理上分散的可用内存区。


需要注意的是，我们这里用的是Freertos封装的malloc和free函数以便我们去自己分配堆内存，但是我们绝对不可以直接使用malloc和free函数去管理内存，这对嵌入式系统的内存是非常危险的。

下面就介绍freertos的相关内存分配函数:

1.分配内存函数:void *pvPortMalloc( size_t xWantedSize )

    xWantedSize：请求分配的内存字节数。注意：实际分配的空间可能会略大于此值，
    因为堆管理器需要额外的空间来存储内存块的管理信息（如块大小、链表指针等）。

    返回值：

    成功：返回指向已分配内存块的指针。分配的内存不会被初始化，其内容是未定义的。
    
    失败：如果堆空间不足，则返回 NULL。

    注意:在中断服务程序（ISR）中谨慎使用

2.释放内存函数:void vPortFree( void *pv )

    pv：指向要释放的内存块的指针。如果指针是 NULL，则函数不执行任何操作（通常是安全的）

    注意:
    绝不能释放不是由 pvPortMalloc 分配的内存。
    绝不能对同一个指针释放两次（双重释放）。
    释放 NULL 指针通常是安全的，但依赖于具体实现，最好避免。
    内核对象（如任务、队列、信号量）有自己专门的创建和删除函数（如 xTaskCreate / vTaskDelete），
    不要尝试用 vPortFree 直接释放它们的内存。应该调用对应的 vTaskDelete, vQueueDelete 等函数。

3.查看甚于空间(堆)的总字节数:size_t xPortGetFreeHeapSize( void )

    返回值：当前空闲内存的大小（以字节为单位）。用uint32_t或者uint8_t接收都可以

4.返回自系统启动以来，堆中曾经达到的最小空闲内存字节数:size_t xPortGetMinimumEverFreeHeapSize( void )

    返回值：历史最小空闲内存大小

size_t xPortGetMinimumEverFreeHeapSize( void )函数和之前的讲解的水位法：uxTaskGetStackHighWaterMark()的功能有点像。但是前者是用于所有任务共同栈用的堆空间的历史最小内存，后者是用于一个任务栈(即一个任
务占用的空间大小)
